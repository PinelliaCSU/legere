# 11 · Agent 协作流程

> 依据 master_plan.md §八（第 730–763 行：四个角色要各自定义职责与工作边界）、03 §3/§4/§5（并行组、文件归属、冲突处理）、05 §10（契约一致性检查）。
> 本文件规定「谁做什么、谁不许做什么、交接什么物」，不规定实现细节。

## 1. 四个角色

### 1.1 架构 Agent（Lead）

| 项 | 内容 |
|---|---|
| 职责 | 维护 02/03/04/05/13 五份冻结契约；批准或拒绝「架构变更」；用 `_template.md` 的 15 节 + `_shared-context.md` 生成每份模块 Prompt；收敛跨模块冲突；最终验收 |
| 输入 | master_plan.md、各模块交付报告、审查 Agent 的结论、集成 Agent 的缺陷单 |
| 输出 | 模块 Prompt（每份 200–400 行，_template.md 第 65 行）；契约修订；验收裁决；`docs/**` 的更新 |
| 明确不做什么 | 不实现任何模块功能（M01–M15 的业务代码不写）；不在某个模块的代码里「顺手」修补契约；不在契约未冻结时放行任何实现任务 |
| 交接物 | 给模块 Agent：一份模块 Prompt + 契约行号引用 + 该模块的写入边界；给集成 Agent：已合并主干 + 契约版本号 |

### 1.2 模块开发 Agent

| 项 | 内容 |
|---|---|
| 职责 | 只实现被指派的那一个模块（M01–M15 之一），严格按其 Prompt 的 §4 功能范围与 §13 验收标准 |
| 输入 | 一份模块 Prompt；`docs/02`–`05`、`13` 的只读契约；前置模块已合并的接口 |
| 输出 | 模块代码 + 测试 + 《交付报告》（`_shared-context.md` I 节的 9 项，第 91–103 行） |
| 明确不做什么 | 不改别人文件（03 §4 归属矩阵）；不新增契约未定义的表/列/Command/事件；不自己拍板任何视觉数值（留 `TODO(ui-confirm)`）；不越界实现别的模块职责（_shared-context.md H 节第 86 行） |
| 交接物 | 给审查 Agent：diff + 交付报告 + 可复现的测试命令；给 Lead：§9「契约问题」与 §8「对其他模块的影响」 |

### 1.3 集成 Agent

| 项 | 内容 |
|---|---|
| 职责 | 按 §6 的顺序把模块合进主干；跑契约一致性检查与端到端脚本；登记并跟踪缺陷；维护样本库 |
| 输入 | 各模块已通过审查的分支；契约版本；测试样本库 |
| 输出 | 集成记录（每次合并的检查结果）、缺陷单（含复现步骤与归属模块）、端到端测试结果 |
| 明确不做什么 | 不在集成期改业务逻辑「让测试通过」——缺陷退回所属模块 Agent（03 §5 第 234 行：需要别的模块的改动，先提接口需求）；不改契约；不动 `docs/module-prompts/**` |
| 交接物 | 给模块 Agent：缺陷单（复现步骤 + 期望/实际 + 归属）；给 Lead：集成报告与阻塞项清单 |

### 1.4 审查 Agent

| 项 | 内容 |
|---|---|
| 职责 | 对照模块 Prompt §13 验收标准与 02 §12 的稳定性承诺，审架构一致性、边界越界、错误处理、测试充分性、性能风险 |
| 输入 | 模块 diff、交付报告、该模块 Prompt、契约文件 |
| 输出 | 结论（通过 / 返工 / 架构变更）+ 逐条缺陷（引用文件:行 + 违反的契约条款）+ 必改项与建议项分离 |
| 明确不做什么 | 不直接改代码（只提交意见，由模块 Agent 落改）；不放宽既有断言以「通过」（H 节第 84 行）；不代替 Lead 批准架构变更 |
| 交接物 | 给模块 Agent：返工清单；给 Lead：是否有架构变更需求 |

## 2. 并行组与串行链

照抄 03 §3（第 187–205 行）：

```text
串行主链（不可并行）:
  M01 -> M02 -> M03

第一批并行（M03 完成后同时开工）:
  A: M04 (library)
  B: M09 -> M10 -> M11   （后端检索链，必须串行）
  C: M12 (bookmarks-progress)
  D: M13 (theme-settings)

第二批并行（前端链，可与第一批同时进行，只依赖 M02）:
  E: M05 -> M06 -> M07 -> M08   （必须串行）

第三批（汇聚）:
  M14 workspace-shell（依赖 A/B/C/D 的接口；先 mock 后接线）
  M15 integration-release（最后）
```

**为什么这样切**（不是排版好看）：

1. `M01 → M02 → M03` 串行，是因为 M02 是**唯一**的 DTO/Command/事件定义处（03 第 42 行），M03 是**唯一**的建表处；让两个 Agent 同时定义 DTO 或建表，等于让两份契约互相冲突（master_plan §7.2 第 715 行「不能让多个 Agent 各自重新设计数据库或 API」）。
2. `M09 → M10 → M11` 串行，是因为 M11 的查询侧必须用 M09 的同一个分词器（04 §7 第 185 行），而 M10 持有任务队列与事件节流（03 第 128 行）；拆开并行只会产生三份各自为政的分词/调度实现。
3. `M05 → M06 → M07 → M08` 串行，是因为视口模型在 M06、命中坐标映射在 M08，都建立在 M05 的 `PageGeometry` 与 `TextItem` 之上（05 §7 第 273、291 行）。这链只依赖 M02，所以能立刻与后端组并行（03 第 205 行）。
4. `M12` / `M13` 彼此无交集（一张表 + 一组 CSS 变量），是干净的并行点；`M04` 独立于检索链，可单独开工。
5. `M14` 汇聚且允许先 mock，是为了让 UI 结构与数据解耦；但 mock 是有期限的（见 §6 第 1 条），不是一种长期架构。

## 3. 文件归属与冲突处理

归属矩阵要点（完整表见 03 §4 第 207–230 行），核心是「一个路径只有一个所有者」：

| 路径 | 所有者 | 其他模块可做什么 |
|---|---|---|
| `src-tauri/src/main.rs`、`lib.rs` | M01 | 仅以「注册一行」方式追加，且在交付报告声明 |
| `src-tauri/src/contracts/**`、`src/contracts/**`、`src/core/ipc.ts` | M02 | 不可修改；变更 = 架构变更 |
| `src-tauri/src/db/**`、`migrations/**` | M03 | 不可修改 |
| `src-tauri/src/library/**` / `index/**` / `jobs/**` / `search/**` | M04 / M09 / M10 / M11 | 不可修改 |
| `src-tauri/src/aux/{bookmarks,progress}/**`、`aux/settings/**` | M12 / M13 | 不可修改 |
| `src/pdf-engine/**`、`src/render/**`、`src/reader/**`、`src/reader/search/**` | M05 / M06 / M07 / M08 | 不可修改 |
| `src/workspace/**`、`src/ui/**` | M14 | `src/ui/**` 可复用但不得改；需要新组件在各自模块目录内建 |
| `src/theme/**`、`src/features/search-panel/**` | M13 / M11 | 不可修改 |
| `docs/**` | Lead | 模块只能在**自己模块的**实现说明小节追加内容 |

冲突处理四条（03 §5 第 232–237 行，逐条照抄其判据）：

1. 需要别的模块提供新接口 → 先在交付报告写「接口需求」，由 Lead 决定是扩展契约还是用现有接口实现；**不得**自己改别人的文件。
2. 两个模块都认为该功能归自己 → 以 03 §2 对应模块卡的「不负责」一栏为准；仍冲突则上报 Lead。
3. 契约字段必须变更 → 标记「架构变更」，列出受影响模块清单，等批准后再改。
4. 发现 03 本身有错 → 提出，不在代码里顺手绕过。

## 4. 一份模块 Prompt 从下发到验收（10 步）

| # | 步骤 | 责任角色 | 落点（可核查的产出） |
|---|---|---|---|
| 1 | 从 03 §3 选定本轮模块，确认其前置模块**已合并到主干并通过验收** | Lead | 待办清单里的一条，注明前置模块与验收引用 |
| 2 | 依 `_template.md` 15 节生成 Prompt，嵌入 `_shared-context.md` A–E 与 H、I 节原文，填充契约行号引用 | Lead | `docs/module-prompts/NN-<slug>.md`（200–400 行） |
| 3 | 冻结写入边界：列出该模块可写的路径，明确「其余路径只读」 | Lead | Prompt 的 §6 与 §15 |
| 4 | 读契约并**先提疑问**：契约缺失/矛盾/不成立项立即上报，不自行发挥 | 模块 Agent | Prompt 的「契约问题」清单（可为空） |
| 5 | 实现 + 自测：Rust `cargo test`、TS `npx vitest run`，边界与错误路径各一例 | 模块 Agent | 代码 + 测试；证据 = 命令 + 输出摘要 |
| 6 | 交《交付报告》9 项（`_shared-context.md` I 节），未验证项必须写「未验证」 | 模块 Agent | 报告文本 |
| 7 | 审查：对照 §13 验收标准 + §5 兼容性清单 + 边界越界检查 | 审查 Agent | 结论（通过/返工/架构变更）+ 逐条缺陷 |
| 8 | 返工：只许在**本模块边界内**改；契约问题升级给 Lead，不在代码里打补丁 | 模块 Agent | 返工后的 diff + 复审记录 |
| 9 | 合并：先 `check-contracts`，再跑本模块测试，最后跑全量集成脚本 | 集成 Agent | 集成记录（三条命令的退出码） |
| 10 | 归档：更新 `docs/**` 对应实现说明小节（仅 Lead 可改，模块只提供素材）；归档交付报告与验收证据 | Lead | docs 更新 diff + 归档记录 |

返工上限：同一模块同一轮返工 ≤ 2 次。第 3 次仍不通过，Lead 必须重新切分该模块 Prompt（缩小范围或补前置模块），而不是继续加压。

## 6. 代码集成顺序与「最后一公里」风险

集成顺序（与 10-development-roadmap.md 的阶段一致，但更细）：`M01 → M02 →（M03）→ M05 → M06 → M07 → M08 →（M04 → M09 → M10 → M11）→ M12 → M13 → M14 → M15`。括号内可与括号外并行，合并到主干时按上述顺序排队，避免「后合的分支覆盖先合的注册行」。

| # | 最后一公里风险 | 表现 | 判据 / 处置 |
|---|---|---|---|
| 1 | mock 分支残留 | M14 长期对着 `__MOCK__` 数据源开发，「看起来能用」但从未接过真实接口 | `grep -R "__MOCK__" src/` 必须为 0；`HomeDataSource` 只能在**一处工厂函数**里切换（13 §8 第 152 行） |
| 2 | 契约漂移 | DTO 改了一处忘了另两处（Rust DTO / TS 类型 / 表列） | `check-contracts.mjs` 退出码 0；D09 第 299 行要求三处同步 |
| 3 | 事件被当作状态源 | 前端只靠 `index://progress` 推算全量状态，丢一条事件即错误 | 05 §4 第 223 行：事件是通知，收到后必须重新拉取或按 payload 增量更新 |
| 4 | FTS 降级分支未测 | 只在 `contentless_delete=1` 可用的机器上测过，降级路径从未运行 | 强制走普通 FTS5 分支后跑全量用例（04 §9 第 206 行） |
| 5 | rowid 复用串号 | 删页后新页复用 rowid，旧命中复活 | 同事务先删 `page_fts` 再删 `page_text`（04 §4 第 158 行），并保留插入-删除-插入回归用例 |
| 6 | 注册行冲突 | 多人往 `main.rs` / `lib.rs` 追加注册，后合分支覆盖先合分支 | 只追加、不重排；合并前 `git diff` 只需看到新增行（03 §4 第 211 行） |
| 7 | 大文件未验证 | V-07 未关闭就宣布性能达标 | 先按保守 `RenderBudget` 起步；不达标按 01 §3 C-07 的固定顺序调参（prefetch → cache → concurrent），不擅自改协议 |

集成期唯一允许的「顺手改动」是修**本次合并自身造成的**冲突（如注册行位置）；其他一律走 §3 的四条冲突规则。
