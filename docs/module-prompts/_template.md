# 模块 Prompt 模板（生成模块 Prompt 时必须严格遵守）

每份模块 Prompt 必须按下列 15 节组织，节标题不得改名、不得删节。内容空洞的节也要写清"本模块此节无内容，原因：…"。

```md
# 模块 <ID>：<模块名>

> 依赖前置：<必须已完成的模块>；被依赖方：<使用本模块的模块>。
> 归属层：<L0–L4>；并行组：<A/B/C/D/E>。

## 1. 模块身份
它在项目中的位置、所属层、在数据流中的角色（3–6 行）。

## 2. 项目背景
原样引入 docs/module-prompts/_shared-context.md 的 A–E 节（不要改写、不要摘要）。

## 3. 模块目标
本次开发要交付的一个可验证结果（一句话）+ 3–6 条分解目标。

## 4. 功能范围（必须完成）
逐条编号，每条可独立验收。

## 5. 非目标（明确不做）
逐条编号，针对"Agent 容易顺手扩张"的地方写清楚。

## 6. 架构约束
- 允许依赖的模块与不允许依赖的模块（点名）
- 必须遵守的接口、状态归属、资源所有权
- 该模块的"不负责"清单与本模块的边界线

## 7. 输入与输出
表格：输入来源 / 数据形态 / 触发时机；输出目标 / 数据形态 / 消费方。

## 8. 接口契约
逐个列出要实现的 Command / 事件 / TS 类型 / trait 方法 / 组件 props，签名必须与
docs/05-api-contracts.md 完全一致；本模块新增但契约未定义的内部接口也要列出。

## 9. 数据结构
涉及的 DTO、表、内部类型；必须与 04/05 一致。字段逐项说明。

## 10. 文件组织
给出建议目录与文件名（含每个文件一句话职责）。允许在不破坏分层与命名规范的前提下调整。

## 11. 实施步骤
有序步骤，每步一个可验证的落点（"做完这步能跑什么"）。

## 12. 测试要求
单元/集成/边界各列出具体用例；Rust 与 TS 分别给命令。

## 13. 验收标准
可判定的条件列表（能被命令或明确观察验证），不接受"功能正常"这类描述。

## 14. 交付报告
原样引入 _shared-context.md 的 I 节。

## 15. 禁止事项
原样引入 _shared-context.md 的 H 节，并按本模块补充 3–6 条具体禁令。
```

写作要求：

1. **具体性**：每一节都要能指导实现，不写"合理设计""注意性能"这类空话；给数值、给名字、给命令。
2. **一致性**：DTO/表/命令/事件/错误码必须与 04、05 逐字一致；不确定就写"引用 docs/05 §x 的定义"。
3. **UI 纪律**：任何视觉/交互取向写进「【待你确认】」列表，并在 §5 非目标里写"不得自行确定视觉方案"。
4. **长度**：单份模块 Prompt 200–400 行。宁精不长，禁止凑字数。
5. **不许发明**：不要编造 pdfjs-dist / Tauri / rusqlite 的 API；不确定的写成"先验证 V-xx，再实现"，并给出验证方法。
